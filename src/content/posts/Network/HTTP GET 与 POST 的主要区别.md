## 前言

学习 HTTP 时，`GET` 和 `POST` 是最容易被问到、也最容易被误解的两个方法。

很多人会直接回答：“GET 参数放在 URL，POST 参数放在请求体。”这句话没有错，但它只说到了表现层面的区别。真正决定它们用法的，是 HTTP 方法背后的语义：这个请求到底是在“读取资源”，还是在“提交数据并改变服务器状态”。

这篇文章会先整理常见 HTTP 方法，再重点说明 GET 与 POST 的核心区别。

## 常见 HTTP 方法

HTTP 定义了多种请求方法，不同方法表达不同语义。

| 方法 | 主要用途 | 常见特性 |
| :--- | :--- | :--- |
| `GET` | 获取资源 | 安全、幂等，参数通常放在 URL 查询字符串 |
| `POST` | 提交数据 | 通常非安全、非幂等，数据通常放在请求体 |
| `HEAD` | 获取响应头 | 类似 GET，但只返回响应头，不返回响应体 |
| `PUT` | 上传或整体更新指定资源 | 幂等 |
| `DELETE` | 删除指定资源 | 通常幂等 |
| `OPTIONS` | 查询服务器支持的通信选项 | 常用于跨域预检 |
| `PATCH` | 部分更新资源 | 通常用于局部修改 |
| `TRACE` | 回显服务器收到的请求 | 调试用途较多，实际生产中较少开放 |
| `CONNECT` | 建立隧道连接 | 常见于代理和 HTTPS 隧道 |

这些方法并不是随便起名的。它们的重点在于告诉服务器和中间代理：“这个请求想表达什么意图”。

## GET 的语义：获取资源

`GET` 的核心语义是获取资源。

比如：

```http title="GET 请求示例"
GET /products/1001?tab=detail HTTP/1.1
Host: example.com
```

这个请求表达的是：我想读取 `products/1001` 这个商品资源，并查看它的详情页。

按照 HTTP 设计，`GET` 应该是安全的。所谓安全，并不是指加密或防攻击，而是指它不应该改变服务器资源状态。

换句话说，多请求几次同一个 GET，不应该导致：

- 创建新订单；
- 修改用户资料；
- 删除某条数据；
- 改变购物车内容。

`GET` 也应该是幂等的。幂等表示同一个请求执行一次和执行多次，结果应该一致。

> [!NOTE] 安全和幂等不是一回事
> 安全强调“不产生副作用”，幂等强调“重复执行结果一致”。GET 通常既安全又幂等。

## POST 的语义：提交并处理数据

`POST` 的核心语义是向服务器提交数据，让服务器根据这些数据做处理。

比如：

```http title="POST 请求示例"
POST /orders HTTP/1.1
Host: example.com
Content-Type: application/json

{
  "productId": 1001,
  "count": 1
}
```

这个请求表达的是：我要提交一份订单数据，请服务器创建订单。

因此，`POST` 通常不是安全的。它可能会改变服务器状态，比如：

- 创建订单；
- 添加购物车；
- 提交评论；
- 上传文件；
- 修改用户信息。

`POST` 通常也不是幂等的。同一个创建订单请求提交两次，可能会生成两张订单。这也是为什么提交表单后刷新页面时，浏览器经常会提示是否重新提交表单。

## GET 与 POST 的核心区别

GET 和 POST 最核心的区别不是“参数放哪里”，而是语义和设计目的不同。

- `GET`：用于读取资源。
- `POST`：用于提交数据，让服务器处理并可能改变资源状态。

基于这个核心区别，它们在技术实现上也表现出很多差异。

## 1. 数据位置不同

GET 的参数通常放在 URL 查询字符串里：

```http title="GET 查询参数"
GET /search?keyword=android&page=1 HTTP/1.1
Host: example.com
```

POST 的数据通常放在请求体里：

```http title="POST 请求体"
POST /login HTTP/1.1
Host: example.com
Content-Type: application/json

{
  "username": "demo",
  "password": "example"
}
```

因为 GET 参数直接出现在 URL 中，所以它会显示在地址栏，也更容易出现在浏览器历史记录、服务端日志、代理日志和分享链接里。

POST 的请求体不会显示在地址栏中，但这并不代表 POST 天然安全。真正保护数据安全的是 HTTPS，而不是 GET 或 POST 本身。

## 2. 安全性与幂等性不同

GET 通常是安全且幂等的。

这意味着重复请求一个 GET，一般不会产生额外副作用。例如反复刷新商品详情页，不应该创建订单，也不应该修改商品数据。

POST 通常不是安全的，也通常不是幂等的。

比如重复提交订单接口：

```http title="重复 POST 可能产生多次副作用"
POST /orders HTTP/1.1
Host: example.com
```

如果后端没有做幂等控制，多次提交可能会创建多笔订单。

实际业务中，如果必须让 POST 具备幂等效果，通常需要额外设计，例如：

- 使用幂等 Token；
- 使用唯一请求号；
- 后端根据业务主键去重；
- 支付、订单等关键场景做重复提交保护。

## 3. 缓存和历史记录不同

GET 因为语义是读取资源，所以它的响应更容易被缓存。

浏览器、CDN、代理服务器都可以根据缓存策略缓存 GET 响应。例如：

```http title="Cache-Control 示例"
Cache-Control: max-age=600
```

另外，GET 请求的 URL 可以被：

- 收藏为书签；
- 保存在浏览器历史记录中；
- 分享给别人；
- 被搜索引擎抓取。

POST 通常表示提交数据并改变状态，因此一般不会被浏览器默认缓存，也不适合被收藏或分享。

当然，HTTP 规范并不是完全禁止缓存 POST，只是实际开发中 POST 缓存非常少见，需要服务端明确设置相关缓存头。

## 4. 数据大小限制不同

GET 的参数放在 URL 中，因此会受到 URL 长度限制。

这个限制并不是 HTTP 协议本身严格规定的，而是由浏览器、服务器、代理和网关共同影响。实际开发中，不应该用 GET 传输很大的数据。

POST 的数据放在请求体中，理论上更适合传输较大的数据，例如：

- 表单；
- JSON；
- 文件；
- 批量数据。

但 POST 也不是完全没有限制。服务器通常会配置请求体大小限制，比如 Nginx、Spring Boot、Node.js 中都可能限制上传大小。

## 5. 使用场景不同

GET 适合读取数据：

- 打开商品详情页；
- 搜索文章；
- 查询用户列表；
- 获取分页数据；
- 下载静态资源。

POST 适合提交数据：

- 登录；
- 注册；
- 提交表单；
- 添加购物车；
- 创建订单；
- 上传文件；
- 提交评论。

举个简单例子：

```text
浏览商品详情页：GET /products/1001
添加商品到购物车：POST /cart/items
```

前者是在读取数据，后者是在改变服务器上的购物车状态。

## 常见误区

### 误区一：POST 一定比 GET 安全

不一定。

POST 的参数不显示在地址栏中，但如果没有 HTTPS，请求体依然可能在传输过程中被窃听。真正决定传输安全的是 HTTPS。

### 误区二：GET 不能带请求体

从协议角度看，GET 请求并不是绝对不能有请求体。但在实际生态中，很多服务器、代理、框架和工具不会按预期处理 GET 请求体。

所以实际开发中，不建议给 GET 设计请求体。

### 误区三：POST 一定不能缓存

POST 不是绝对不能缓存，只是默认语义和常见使用方式决定了它很少被缓存。大多数业务场景里，也不应该依赖 POST 缓存。

## 如何选择 GET 和 POST

可以用一句话判断：

> 如果操作是在读取数据，优先使用 GET；如果操作会提交数据并改变服务器状态，使用 POST。

也可以用下面这张表快速记忆：

| 对比项 | GET | POST |
| :--- | :--- | :--- |
| 语义 | 获取资源 | 提交数据并处理 |
| 参数位置 | URL 查询字符串 | 请求体 |
| 是否安全 | 通常安全 | 通常不安全 |
| 是否幂等 | 通常幂等 | 通常非幂等 |
| 是否容易缓存 | 容易缓存 | 通常不缓存 |
| 是否适合收藏/分享 | 适合 | 不适合 |
| 数据大小 | 受 URL 长度影响 | 受服务端请求体限制 |
| 典型场景 | 查询、详情页、搜索 | 表单、订单、上传、修改 |

## 总结

GET 和 POST 的区别，根本上来自语义。

GET 表达的是“我要读取资源”，因此它应该安全、幂等，也更适合缓存、书签和分享。

POST 表达的是“我要提交数据，请服务器处理”，因此它通常会改变服务器状态，也更适合创建资源、提交表单、上传文件和执行业务操作。

所以在实际开发中，不要只根据“参数放 URL 还是请求体”来选择 GET 或 POST。更重要的是先判断这个接口到底是在读取数据，还是在修改数据。

读数据，用 GET。

改状态，用 POST。
